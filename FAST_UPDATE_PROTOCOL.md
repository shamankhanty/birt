# Быстрое обновление дашборда

Цель: еженедельное обновление данных не должно превращаться в повторную разработку проекта и полное чтение репозитория.

## 1. Базовая модель работы

- `main` — только опубликованная рабочая версия.
- Любое обновление сначала выполняется в отдельной ветке `update/YYYY-MM-DD-*`.
- В `main` изменения попадают одним squash-merge только после успешных проверок и отдельной команды владельца на публикацию.
- Несколько правок одного обновления не должны запускать несколько production deploy.

## 2. Обычное еженедельное обновление данных

1. Не перечитывать весь репозиторий и историю чатов.
2. Использовать текущий `main` как baseline.
3. Распаковать только новый пакет исходных выгрузок во временный каталог.
4. Запустить `python3 scripts/weekly_update_pipeline.py <input> --stage`.
5. Сначала читать только компактный `validation/pipeline/latest-scan.json` и перечень реально изменённых файлов.
6. Если результат `PASS`, не отправлять исходные таблицы на повторный ИИ-анализ и не пересчитывать вручную уже формализованные показатели.
7. Если `WARNING`, анализировать только предупреждения и затронутые показатели.
8. Если `FAIL`, останавливать обновление и разбирать только конфликтующие источники/методику.
9. Не заменять отсутствие данных нулём. Не считать изменение источника, периода или методики динамикой.

## 3. Что проверять

### Data-only update

Обязательны:

- JSON/UTF-8 integrity;
- release consistency;
- `npm run validate:refactor`;
- `node --test tests/*.test.mjs`;
- single-file offline build и проверка Pages artifact.

Полный `vinext build` для изменения только JSON-данных не требуется: он выполняется в production CI только при изменении кода.

### Изменение кода или интерфейса

Дополнительно обязателен полный `npm run build`.

### Изменение import pipeline

Дополнительно обязателен `python3 scripts/pipeline/adapter_selftest.py`.

## 4. GitHub

- Не делать последовательные production-коммиты в `main` для исправлений одного обновления.
- Все промежуточные изменения накапливать в рабочей ветке.
- Перед публикацией — один PR, одна финальная проверка, один squash-merge, один GitHub Pages deploy.
- Документационные изменения (`README`, `STATE`, `OPEN_ISSUES`, `docs`, `methodology`, `data_sources`) сами по себе не должны запускать Pages deploy.

## 5. Что должен делать ИИ

ИИ нужен для:

- новой/изменённой методики;
- неоднозначного сопоставления источников;
- конфликтов числителя, знаменателя, периода или МО;
- новых типов выгрузок;
- изменения интерфейса или логики расчёта.

ИИ не нужен для повторного чтения всех исходников, если детерминированный pipeline дал `PASS`.

## 6. Отчёт владельцу

После обычного обновления сообщать кратко:

- какие новые выгрузки приняты;
- какие наборы данных изменились;
- `PASS / WARNING / FAIL`;
- какие показатели требуют внимания;
- готово ли обновление к публикации.

Не перечислять внутренние отладочные итерации, если они не влияют на результат пользователя.
