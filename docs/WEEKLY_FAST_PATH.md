# Еженедельное обновление дашборда: быстрый контур

## Управленческое правило

Обычное недельное обновление данных не является задачей разработки. Для него используется детерминированный конвейер и лёгкий режим модели. Полный анализ проекта выполняется только при изменении методики, структуры, расчётной логики или при блокирующем FAIL.

## Режимы работы

### 1. Обычное недельное обновление — fast path

Использовать Terra или другой быстрый режим.

Вход:
- последний успешный артефакт GitHub Actions `dashboard-source-workspace`;
- новый пакет исходных отчётов за неделю.

Порядок:
1. Развернуть текущий source workspace.
2. Распаковать новый пакет отчётов в отдельную папку.
3. Запустить `python3 scripts/weekly_update_pipeline.py <input> --stage`.
4. Читать только `staging-manifest.json`, список изменённых файлов и сообщения FAIL/WARNING.
5. Не перечитывать весь репозиторий и историю чата, если pipeline = PASS.
6. При PASS сверить итоговые региональные факты, периоды, числители/знаменатели и только изменившиеся показатели.
7. До явной команды пользователя публикацию не выполнять.
8. После разрешения публикации применить только подтверждённые изменения, обновить baseline и дождаться SUCCESS GitHub Pages.

ИИ не должен повторно рассчитывать показатели, которые уже рассчитаны адаптерами.

### 2. Эскалация — сложный режим

Переходить на Sol/усиленное рассуждение только если есть:
- FAIL адаптера или формальной валидации;
- изменение формулы, числителя, знаменателя, источника или периода;
- новая медицинская организация, которую нельзя однозначно сопоставить;
- новая структура файла, неизвестный источник или конфликт периодов;
- изменение рейтинга, применимости, исключений или методики;
- изменение интерфейса/архитектуры дашборда;
- регрессия, которую не удалось локализовать стандартными тестами.

Обычный WARNING без методологического риска не является основанием читать весь проект.

## Обязательные правила данных

- Отсутствие данных не заменять нулём.
- Один показатель рассчитывается один раз из утверждённого источника.
- Изменение методики, источника или исправление ошибки не считать динамикой.
- Для месячного рейтинга использовать только последний полный календарный месяц.
- Неполный месячный файл `500+` не включать в месячный рейтинг; использовать только для оперативного недельного контроля раздела 02.
- Для долевых показателей проверять числитель, знаменатель, период и источник.
- Публикация только после явной команды пользователя.

## Что должен возвращать fast path

Краткий отчёт:
- дата среза;
- сколько файлов распознано / не распознано;
- какие семейства источников обновились;
- какие показатели реально изменились;
- PASS / WARNING / FAIL;
- перечень только существенных предупреждений;
- статус публикации.

Не выводить внутренние отладочные итерации в пользовательскую историю версий. Обновления одного дня объединять; недельные технические изменения агрегировать в одну пользовательскую запись.

## GitHub

Каждый успешный deploy создаёт артефакт `dashboard-source-workspace` — компактную точку входа для следующего обновления. Это позволяет следующему чату получать актуальное состояние проекта одним артефактом вместо чтения всего репозитория.

CI обязан:
- проверять UTF-8 и валидность JSON до расчётов;
- проверять согласованность версии baseline и runtime;
- проверять, что категории ошибок РЭМД и детализация по МО хранятся раздельно;
- выполнять расчётные и регрессионные тесты;
- запускать полный self-test адаптеров при изменении pipeline-кода;
- публиковать только после успешной сборки.
