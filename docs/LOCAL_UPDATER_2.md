# BIRT Local Updater v2

Единственная пользовательская точка запуска — `UPDATE-BIRT.ps1`.
По умолчанию выполняется один полный проход по реальному INBOX:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\UPDATE-BIRT.ps1
```

Политика Windows меняется только для запускаемого процесса. Можно указать `-Inbox`,
включить наблюдение `-Watch -Interval 60` или повторную обработку `-Force`.
Без Force одинаковый пакет пропускается только при неизменном коде и baseline.
Нужны Python 3.11+, openpyxl, Node.js, npm и установленные зависимости package-lock.

## Что получается

`REPORTS/latest.json` содержит управленческий итог. Каждый запуск хранит отдельный
каталог с `report.json`, входным снимком `input/`, кандидатом `candidate/app/`,
проверками каждого показателя `candidate/transactions/`, журналом сборки `build.log`
и **автономным HTML-дашбордом с ZIP в `dashboard/`**. HTML использует данные кандидата.
Подробная диагностика не выводится в консоль. Источники и рабочие production JSON
не перезаписываются; commit, push, deploy отсутствуют. Копии хранятся без автоудаления.

## Состояния

* READY — все поступившие поддерживаемые показатели прошли проверки; независимый
  исторический replay подтвержден для подготовленных показателей; неизвестных источников нет.
* PARTIAL — безопасный кандидат собран, но есть отклоненные или неизвестные источники
  либо не подтвержден исторический replay. Корректные показатели доступны в HTML.
* STOP — неисправна инфраструктура проверок/сборки, baseline невалиден или безопасный
  итоговый кандидат невозможно подтвердить. Такой запуск не кешируется как успешный.

Отсутствующие в INBOX показатели перечисляются как RETAINED с причиной.
Каждый показатель собирается в отдельной транзакции, проходит формальную валидацию
и повторную обработку из той же baseline. Только его изменения переносятся в кандидат.
При ошибке сохраняется целиком исходное значение вместе с датой, периодом, деталями
и месячным рейтингом. Ошибка одного показателя не откатывает успешно подготовленные.
Системный сбой валидатора не трактуется как ошибка отдельной выгрузки.

Структура листов и заголовков определяет тип XLSX независимо от имени. Период из
заголовка имеет приоритет над датой формирования и именем файла. Неоднозначность
типа, повтор одного периода и повреждение книги отклоняются. Списки исключений
из приложений не используются как полный набор МО или знаменатель.

СЭМД 122/228 читает OID и знаменатель обеих известных схем ФОМС; отсутствие пары
не превращается в пустой успешный набор. Строки «Итого» не становятся МО.
MAX принимает накопительный источник с 01.01, месячный источник сверяет как контроль;
проверяет строку «Итого» и не суммирует контроль с накопительными значениями.
МО разрешаются через общий runtime справочника, без нечеткого сопоставления.
Врачебные показатели имеют индивидуальные периоды; частичный месяц не меняет рейтинг.

## Historical replay

Повторяемость текущего импорта и историческая эквивалентность — разные проверки.
`UNAVAILABLE` означает отсутствие подтвержденных исходников/эталона; это не PASS.
Поддерживается `ARCHIVE/historical-replay.json` рядом с INBOX:

```json
{
  "cases": [{
    "metric": "birth",
    "baselineApp": "C:/BIRT-Data/ARCHIVE/before/app",
    "expectedApp": "C:/BIRT-Data/ARCHIVE/approved/app",
    "sourceSha256": "SHA256 исходного XLSX",
    "source": {
      "family": "birth_certificates",
      "path": "C:/BIRT-Data/ARCHIVE/source.xlsx",
      "name": "source.xlsx",
      "startDate": "2026-01-01",
      "endDate": "2026-09-11",
      "status": "PASS"
    },
    "files": ["mo-data.json", "mo-details.json", "monthly-mo.json"]
  }]
}
```

Для парного показателя нужен `partner` с метаданными второго источника.
Эталон должен быть независимо подтвержденным результатом исторического обновления,
а не копией текущего кандидата. Проверяются SHA-256 источника и семантическое равенство
результата с эталоном; отсутствие покрытия всех подготовленных показателей оставляет PARTIAL.
Защита live apply не снимается. Даже READY не выполняет публикацию автоматически.

Коды завершения: 0 — READY/PARTIAL или нет новых файлов, 2 — STOP,
3 — файлы меняются при копировании; обработка отложена.

## Проверки

`python -m unittest discover -s tests -p test_local_updater_v2.py` — regression Updater.
`python scripts/pipeline/adapter_selftest.py` — 21 адаптер и staging end-to-end.
`node --test tests/*.test.mjs` — полный набор после production build.
Каждый реальный запуск дополнительно выполняет baseline validation, calculation/
metadata equivalence, валидацию каждой транзакции и всего кандидата, повторяемость
импорта и автономную сборку. Формальные ошибки не игнорируются ради READY.

## Финальная приёмка 20.09.2026

Статистика `statistics` разделяет `expectedIndicators` (ожидаемые Updater показатели),
`receivedIndicators` (получили источники), `preparedIndicators`, `unchangedIndicators`
(тот же подтверждённый результат), `retainedInvalidIndicators` (поступивший источник
не принят) и `missingSourceIndicators`. Поэтому 27/29 означает долю подготовленных
среди поступивших, а не среди всех 34 поддерживаемых показателей.

Historical replay подтверждает новую реализацию импорта, а не каждую новую дату.
После успешного подтверждения сохраняется `REPORTS/historical-qualification.json`:
происхождение manifest, контрольные суммы реализации, правил, справочника, baseline,
исходников и независимого эталона, а также результаты сравнений. При неизменных
контрольных суммах доказательство используется повторно; обычный новый пакет INBOX
не заставляет заново исполнять исторический импорт. Изменение кода, правил,
baseline либо проверочных материалов отменяет повторное использование.
Проверки текущего пакета и целостности доказательства выполняются всегда.

**Bootstrap текущего v5.4.5 не разрешён имеющимися документами.**
`baseline/RELEASE_5.4.5.md` прямо называет его неопубликованным кандидатом.
В `STATE.md` production указан как v5.4.3, несмотря на заголовок v5.4.5.
Контрольные суммы локальных JSON подтверждают их целостность, но не публикацию
версии и не правильность преобразования Excel новой архитектурой.
Поэтому текущий результат — UNAVAILABLE, новый доверенный baseline не создавался.

Для первоначального подтверждения нужны предыдущий `app/` и независимо утверждённый
результат `app/` одного исторического обновления, а также его исходники за те же периоды:

* на 11.09.2026: ПР_2 (оба показателя ЕПГУ), госпитализации + РЭМД,
  законченные амбулаторные случаи, свидетельства о рождении и смерти;
* на 11.09.2026: закрытые случаи ДОГВН/ПМО с СЭМД 122/228 и парная выгрузка
  профилактических обращений ФОМС; имена сохранены в `app/preventive-semd-audit.json`;
* накопительные MAX ТМК/ЛВН, краткий ввод, ФАП/ФП, АСУ СМП, ТМК РЭМД,
  ЭЛМК и пять выгрузок ТВСП на 11.09.2026;
* врачебная выгрузка среза 11.09.2026, указанная в `app/physician-weekly-snapshot.json`;
* отказы РЭМД за полную неделю 07–13.09.2026 и ЭПЛ за недели
  31.08–06.09 и 07–13.09.2026 для подтверждения соответствующих адаптеров.

Можно использовать другой независимо подтверждённый исторический пакет с
согласованными исходниками, периодами и эталоном. Excel на 17.09 из текущего INBOX
не заменяет отсутствующий пакет на 11–13.09. ARCHIVE при проверке пуст.
